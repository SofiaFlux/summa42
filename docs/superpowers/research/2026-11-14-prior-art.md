# Prior art worth learning from (2026-11-14)

A reading list for the `DESIGN` cards of the
[development plan](../plans/2026-11-11-development-plan.md). Each entry names
the pattern to take, the card it informs, and what to avoid. The rule for all
of them: take the pattern, not the dependency. Section 8 of the plan rules out
heavy infrastructure for one Owner on one host, so a new dependency still needs
a card that says so (rule R6).

This note is direction, not a decision. Product facts here are from general
knowledge and have not been rechecked against current documentation; a spec
that relies on one must cite the primary source.

## Highest value

### GitHub Scientist: shadow comparison

Scientist replaces code on a live system by running the control (old) and the
candidate (new) paths together. Only the control result is used; mismatches are
recorded. This is the shape of shadow mode (M6-T3) and of replacing a model
executor with a compiled script (D5, M6-T8).

Take: how they compare results (custom comparators, ignoring known harmless
differences), sampling so that the candidate does not run on every call, and
treating a candidate exception as a mismatch, not a crash.

Avoid: running a candidate that has external effects. In Summa42 a shadow run
prepares no operation and takes no lease (`TestShadowCausesNoEffect`).

### Process mining: detecting routines

Process mining reconstructs the actual process from an event log. Its terms map
almost one to one: a *case* is a workflow case, an *activity* is a stage or an
Owner action, a *variant* is a distinct sequence of activities. Frequent
variants are candidate routines.

Take: variant similarity measures for M6-T8's question "when are N Attempts
the same", and conformance checking (does a new case still follow the
variant?) as a shadow signal.

Avoid: process maps as an end product. Detection here ends in a proposal with
evidence (M6-T2), never a chart.

### Temporal, Restate, DBOS: durable execution

These separate deterministic orchestration code (the Box) from unreliable
steps (Attempts). On restart they replay the recorded history instead of
re-executing effects.

Take:

- versioning of workflows that are still running, which M6-T8 needs when a
  script version changes while a case is in progress;
- signals: a human input delivered into a running workflow (Owner decisions);
- DBOS keeps workflow state in the application database itself, which is
  close to the single SQLite Box.

Avoid: adopting Temporal itself. It needs its own cluster and would replace
the kernel instead of informing it.

### Biscuit and Macaroons: authority only narrows

A Biscuit or Macaroon token carries caveats. Any holder can add one and hand
the token on; nobody can remove one. Attenuation is enforced by cryptography,
not by code that checks database rows. That is Vision Article 6 ("authority
may contract autonomously, never expand autonomously") as a data format.

Take: consider it for standing delegations (M5) and automation mandates
(M6-T4): a delegation as an Owner-signed token, and a Task's authority as an
attenuation of it.

Avoid: tokens as the only record. Audit (Article 23) still needs the durable
record of who attenuated what and why.

### Cedar and OPA: analyzable policy

Cedar's language is deliberately restricted so that an analyzer can prove
properties, for example that a policy change grants nothing new. OPA with Rego
is more expressive and harder to reason about.

Take: Cedar's restrictions as a design guide for the policy profile, so that
tests such as `TestAdoptionNeverCreatesDelegation` can become a check over the
policy itself.

Avoid: Rego-style general logic in policy. Policies that nobody can read are
not governance.

### TUF, Sigstore, in-toto: self-update and evidence

TUF (The Update Framework) is designed for systems that update themselves:
separate key roles (root, targets, snapshot, timestamp), protection against
rollback to an old vulnerable version and against freezing on stale metadata,
and survival of the compromise of some keys. That is the threat model of A3
(M8), where a Cube replaces its own Box binary.

in-toto records each supply-chain step as a signed attestation and checks that
the chain is complete. Sigstore makes signing and transparency logs cheap. Both
are close to Summa42's evidence model and to the signed backup manifest.

Take: TUF's roles and rollback rules for M8; the in-toto layout idea for
"this release was built from this commit, reviewed by this reviewer, tested by
this gate".

### TigerBeetle and FoundationDB: deterministic simulation testing

Both run the whole system in a simulator with a controlled clock, scheduler and
injected faults, so a rare interleaving is reproduced from a seed instead of
hoped for. TigerBeetle is also a double-entry ledger.

Take: deterministic simulation for the Box's concurrency tests. Running
`TestCloseConcurrentReplay` 600 times finds flakes by luck; a seeded scheduler
finds them by construction. Double-entry accounting for the resource and money
ledger (M3).

### Dagster asset checks and data tests: output contracts

Dagster models data as assets with checks attached; dbt tests and Great
Expectations do the same for tables. A job that ran is not an asset that is
correct.

Take: the shape of M6-T8's output contract (schema, invariants, freshness,
row counts) and, for the first product (Data as a Service, M7), checks on
every delivered dataset.

## Smaller lessons

- **Inspect and the SWE-bench harness** (M1A-T6): sandboxed tasks, scorers
  independent of the agent, recorded transcripts. Relevant to the parity
  benchmark and to the fabricated-review incident.
- **Kubernetes operators** (Constructors, Q43): a reconcile loop that compares
  desired and actual state and does nothing when they match. "No action
  required" is a valid result.
- **SRE error budgets** (M6-T4, M5): a budget of allowed failures per window;
  spending it contracts autonomy automatically, regaining it needs a decision.
- **gVisor, Firecracker, Landlock** (M9): user-space kernel, micro-VM and
  in-kernel self-restriction, with different costs and guarantees.

## Autonomy after a grant: public reporting on ARTEX

ARTEX is an open-source multi-agent penetration-testing framework that was
used in real attacks in 2026. Only its public reporting is relevant here, as
evidence about long autonomous runs; nothing offensive is taken from it.

What the reporting shows:

- Agents ran for hours on several targets in parallel after an operator set a
  single goal. Long autonomy after one grant is technically achievable today.
- Some agents reported success that had not happened: an API response that
  looked like success was taken as the outcome. This is the failure Articles
  11 and 21 exist for: an unverified result is `UNKNOWN`, not success.
- Operators still intervened at key decision points. Sources disagree on how
  autonomous the runs really were.
- Poorly configured agents left enough traces to reconstruct their work.

What Summa42 takes from it: autonomy inside a grant is the goal (plan
section 2.6, standing delegation in M5, mandates in M6), but the grant is an
Owner-signed ceiling that can only contract, every claimed effect needs
independent verification, and the audit trail is designed, not accidental.
ARTEX's autonomy has no ceiling except the operator's tools.
